# Программа управления данными ООО «ШопЭксперт» (Data Governance Charter)

**Версия:** 1.0
**Автор:** Никита Ф., группа ВМО-4X
**Дата:** октябрь 2026

---

## 1. Контекст и постановка проблемы

ООО «ШопЭксперт» — интернет-магазин бытовой техники и электроники.
Работает 6 лет, в штате 120 человек. Каналы продаж: сайт, мобильное
приложение, колл-центр; складская инфраструктура в трёх городах.

За последние полгода руководство зафиксировало серию инцидентов,
указывающих не на ошибки отдельных сотрудников, а на **системный
пробел в управлении данными**:

1. Клиенты жалуются на расхождение итоговой суммы заказа в личном
   кабинете и в банковском SMS.
2. Маркетинг не может сойтись в цифре «активный клиент»: CRM и
   рекламный кабинет дают разные значения.
3. Операторы поддержки видят разные версии истории одного и того же
   заказа в зависимости от открытой системы.
4. Запрос клиента на удаление персональных данных обрабатывался 3 дня
   только на этапе поиска, где эти данные вообще лежат.

Причина — отсутствие формализованной операционной модели Data
Governance: роли не назначены, политики не сформулированы, единый
реестр данных не ведётся.

Цель документа — зафиксировать минимально достаточную программу
управления данными для «ШопЭксперт», построенную по принципу
**Non-Invasive Governance**: не создавать новые должности, а
формализовать уже существующую де-факто ответственность.

## 2. Критичные домены данных

Отобраны 5 доменов, непосредственно связанных с выявленными
инцидентами.

**Домен 1. Клиентская база.**
Ключевые сущности: профиль, контактные данные, сегмент, признак
активности, история обращений.
Потребители: маркетинг, поддержка, отдел продаж.
Обоснование критичности: нет единого определения «активный клиент» —
маркетинг и CRM расходятся в цифрах.

**Домен 2. Заказ.**
Ключевые сущности: номер, состав, статус, итоговая сумма, история
изменений.
Потребители: продажи, поддержка, логистика, бухгалтерия.
Обоснование критичности: операторы видят разные версии одного заказа.

**Домен 3. Денежные операции.**
Ключевые сущности: платёж, сумма, способ, статус, возврат, привязка к
заказу.
Потребители: бухгалтерия, продажи, поддержка.
Обоснование критичности: сумма в кабинете не сходится с банковской.

**Домен 4. Персональные данные.**
Ключевые сущности: ФИО, телефон, e-mail, адрес доставки, согласия на
обработку.
Потребители: поддержка, юристы, бухгалтерия.
Обоснование критичности: регулируется 152-ФЗ, есть право на удаление и
требование локализации.

**Домен 5. Ассортимент и склад.**
Ключевые сущности: карточка товара, цена, категория, остатки по
складам.
Потребители: сайт, приложение, склад, маркетинг.
Обоснование критичности: прямо влияет на продажи, цены и доступность.

## 3. Роли: владельцы и стюарды

Для каждого домена назначены **Data Owner** (бизнес-решения) и
**Data Steward** (операционная работа с данными). Выбор обоснован
принципом Non-Invasive: роль получает тот, кто уже де-факто выполняет
эту функцию.

**1. Клиентская база.**
Data Owner: директор по маркетингу.
Data Steward: аналитик CRM.
Почему именно они: маркетинг формулирует требования к клиентским
данным, аналитик CRM ежедневно сверяет выгрузки и первым ловит
расхождения определений.

**2. Заказ.**
Data Owner: коммерческий директор.
Data Steward: старший оператор отдела заказов.
Почему именно они: коммерческий директор отвечает за выручку, оператор
ведёт заказы руками и видит ошибки раньше всех.

**3. Денежные операции.**
Data Owner: финансовый директор.
Data Steward: бухгалтер-ревизор.
Почему именно они: финдиректор отвечает за денежные потоки, ревизор
ежедневно сверяет выписки банка с учётной системой.

**4. Персональные данные.**
Data Owner: начальник юридического отдела.
Data Steward: DPO (ответственный за обработку ПД).
Почему именно они: юрист задаёт рамки по 152-ФЗ, DPO ведёт реестр
систем и обрабатывает запросы субъектов.

**5. Ассортимент и склад.**
Data Owner: директор по закупкам.
Data Steward: категорийный менеджер.
Почему именно они: закупки отвечают за ассортимент и цены, категорийный
менеджер ведёт карточки и остатки по складам.

**Сквозные роли.**
Data Custodian — руководитель ИТ-отдела. Отвечает за техническую
сторону: СУБД, доступы, бэкапы, интеграции.
Data Governance Council — коллегиальный орган из Owners всех доменов,
финдиректора и юриста. Собирается раз в месяц, утверждает политики,
разрешает меж-доменные конфликты.

## 4. Политики управления данными

Пять политик по единому шаблону: *цель → область действия → правила →
ответственный за исполнение*. Две из них (4.2 и 4.4) прямо ссылаются
на требования 152-ФЗ и GDPR.

### 4.1. Политика разметки данных по уровню чувствительности

**Цель.** Ввести единую шкалу чувствительности, чтобы к каждому
набору данных применялись соразмерные меры защиты.

**Область действия.** Все информационные системы «ШопЭксперт»: сайт,
мобильное приложение, CRM, учётная система, рекламные кабинеты,
корпоративные файловые хранилища.

**Правила.**
1. Каждому полю присваивается один из четырёх уровней: открытые, для
   внутреннего пользования, коммерческая тайна, персональные данные /
   ограниченный доступ.
2. Соответствие «уровень → меры защиты» фиксируется в реестре данных
   (data catalog).
3. Реестр пересматривается дважды в год либо при изменении
   законодательства.
4. Поля уровня «персональные данные» дополнительно шифруются при
   хранении и при передаче.

**Ответственный за исполнение.** Data Governance Council (утверждение
реестра), Data Steward каждого домена (актуализация), Data Custodian
(реализация технических мер).

### 4.2. Политика качества и согласованности данных

**Цель.** Устранить расхождения между системами и обеспечить
достоверность критичных полей.

**Область действия.** Критичные поля доменов «Клиентская база»,
«Заказ», «Денежные операции».

**Правила.**
1. У каждого критичного поля есть владелец, метрика и целевое
   значение. Метрики: полнота, точность, согласованность,
   актуальность.
2. Автоматические проверки запускаются ежедневно, ручной аудит Steward
   проводит раз в квартал.
3. Ключевые сверки:
   - итог заказа равен сумме денежных операций по этому заказу;
   - единое определение «активного клиента» для CRM и рекламы;
   - единая история заказа во всех системах, где она отображается.
4. Обнаруженные расхождения попадают в журнал инцидентов качества;
   срок исправления — не более 5 рабочих дней.

**Ответственный за исполнение.** Data Steward (ежедневный контроль),
Data Custodian (автоматические проверки).

### 4.3. Политика доступа к данным (152-ФЗ, GDPR — минимизация)

**Цель.** Обеспечить, чтобы доступ к данным получали только те, кому
он действительно нужен, и только в необходимом объёме. Реализует
принцип data minimisation (GDPR, ст. 5; 152-ФЗ, ст. 5).

**Область действия.** Все сотрудники, подрядчики и внешние системы,
имеющие доступ к данным компании.

**Правила.**
1. Доступ выдаётся по принципу least privilege и только при наличии
   служебной необходимости.
2. Для уровня «коммерческая тайна» требуется письменное обоснование
   руководителя и одобрение Data Owner домена.
3. Для уровня «персональные данные» дополнительно нужны:
   - обучение по 152-ФЗ;
   - NDA;
   - правовое основание обработки — согласие субъекта (GDPR, ст. 6;
     152-ФЗ, ст. 9).
4. Пересмотр прав — ежеквартально; при увольнении или переводе —
   в течение 1 рабочего дня.
5. Все действия с персональными данными журналируются.

**Ответственный за исполнение.** Data Owner (утверждение), Data
Custodian (выдача и отзыв), DPO (контроль соответствия).

### 4.4. Политика жизненного цикла и удаления данных (152-ФЗ, GDPR — право на удаление)

**Цель.** Соблюсти установленные законом сроки хранения, не раздувать
боевую БД и гарантировать исполнение права субъекта ПД на удаление.

**Область действия.** Домены «Заказ», «Денежные операции»,
«Клиентская база», «Персональные данные».

**Правила.**
1. Заказы старше 3 лет с момента закрытия переносятся в архивное
   хранилище.
2. Персональные данные хранятся не дольше, чем этого требует цель
   обработки, и не дольше 5 лет — для документов, попадающих под
   бухгалтерское хранение.
3. Запрос субъекта на удаление ПД (GDPR, ст. 17; 152-ФЗ, ст. 21)
   обрабатывается в течение 30 календарных дней, с фиксацией факта
   удаления во всех системах реестра.
4. Ведётся реестр систем, в которых присутствуют ПД, — это сокращает
   время поиска данных при запросе.
5. Персональные данные граждан РФ хранятся на серверах на территории
   РФ (152-ФЗ, ст. 18).

**Ответственный за исполнение.** Data Steward ПД (ежеквартальная
проверка), Data Custodian (архивация и удаление), юрист (контроль
соответствия).

### 4.5. Политика реагирования на инциденты

**Цель.** Быстро обнаруживать, локализовывать и устранять инциденты,
минимизируя ущерб.

**Область действия.** Все системы и домены.

**Правила.**
1. Инциденты делятся на три уровня:
   - критический — утечка ПД, потеря домена, массовое расхождение
     (более 5% записей);
   - средний — расхождение по отдельным записям, недоступность
     системы более часа;
   - низкий — единичные ошибки.
2. Реакция: критический — немедленно, уведомление руководства и
   юриста в течение 1 часа; средний — в течение рабочего дня;
   низкий — в течение 5 рабочих дней.
3. При утечке ПД: уведомление регулятора — Роскомнадзора по 152-ФЗ и
   надзорного органа по GDPR в течение 72 часов (GDPR, ст. 33),
   уведомление пострадавших клиентов.
4. По каждому инциденту — постмортем и запись в журнал инцидентов.

**Ответственный за исполнение.** Data Governance Council
(координация), Data Steward (локализация), Data Custodian
(техническое устранение), юрист (уведомление регулятора).

## 5. RACI-матрица

Расшифровка: R — исполнитель; A — ответственный за результат (ровно
один на строку); C — консультирует до решения; I — информируется по
факту.

**Процесс 1. Оформление доступа нового сотрудника к домену.**
Data Owner — A. Data Steward — C. Data Custodian (ИТ) — R. Аналитик /
пользователь — I.

**Процесс 2. Устранение ошибки в критичном поле.**
Data Owner — I. Data Steward — A. Data Custodian (ИТ) — R.
Аналитик / пользователь — C.

**Процесс 3. Подключение нового источника данных.**
Data Owner — A. Data Steward — C. Data Custodian (ИТ) — R.
Аналитик / пользователь — I.

**Процесс 4. Исполнение запроса клиента на удаление ПД.**
Data Owner — A. Data Steward — R. Data Custodian (ИТ) — R.
Аналитик / пользователь — I.

**Процесс 5. Изменение схемы таблицы домена.**
Data Owner — A. Data Steward — C. Data Custodian (ИТ) — R.
Аналитик / пользователь — I.

**Контроль.** В каждом процессе ровно одна буква A. Если где-то
появляется вторая — распределение ответственности не завершено.

---

## 6. Что даёт эта программа

Документ описывает минимально достаточную операционную модель
управления данными для «ШопЭксперт»:

1. 5 критичных доменов с обоснованием.
2. Owner и Steward для каждого домена — по логике Non-Invasive
   Governance.
3. 5 политик по единому шаблону, две из них привязаны к требованиям
   152-ФЗ и GDPR.
4. RACI-матрица на 5 процессов с единственным A в строке.

Следующий шаг — утверждение документа на Data Governance Council и
постановка регулярных проверок (ежедневных автоматических и
ежеквартальных ручных).
